## 失败与修正记录

一条一条记：现象 → 真因 → 正确做法。写清是"桥的 bug"还是"游戏规则"。

| 现象 | 真因 | 正确做法 |
|---|---|---|
| 移动无位移 | 身体四行里有一行是实心（常见是头顶那格） | 用 `scan` 取整张实心图，按四行判断，从上往下挖穿后再走 |
| 放置 0 成功 | 目标格只有植物/墓碑/家具（不是支撑），或在空中 | 用 `tile.solid` 判支撑；家具走 PlaceObject |
| 挖了但没掉落、也看不到挥动 | `PreItemCheck` 返回了 false，取消 `ItemCheck_Inner` | 返回 true；挖掘默认走原版 ItemCheck |
| 后台什么都不会发生 | 单人失焦时 `Main.DoUpdate` 整帧早退（`gamePaused=true`） | 后台线程顶住 `Main.hasFocus` |
| 长脚本跑到一半全毁 | 脚本没有应变：缺料/挡路/被打断就继续硬走 | 小步闭环：看→做→回读→再决定 |
| 建好的房子重启后全没了 | ①`PlaceTile(forced)`/直接 `PlaceWall` 的格子不合法，重载被丢；②杀 `dotnet` 控制台进程导致没存档 | 只走游戏物品使用路径；关**游戏窗口**（`SDL_app` 的 WM_CLOSE）正常退出 |
| 怪物/僵尸穿过墙 | 同上，格子不是游戏认可的方块 | 同上 |

### 第 10-12 轮：地下作业的两次死亡（教训）

事实：两次下挖都在黑暗里进行，**两次死亡**（第一次挖穿自家地板、第二次被地下敌对生物/环境杀死），
物品没丢，但时间全废。

根因不是"运气差"，是三条纪律都没做到：

1. **没照明就下挖**：屏幕全黑时截图看不见任何东西（水/岩浆/怪物），等于关掉了感知。
   玩家会边挖边插火把；代理必须同样，而且要在**进入新区域前**先放光。
2. **没有每步读处境**：血量/呼吸/是否泡水只在阶段结束时看，太晚。现在 `state` 已带
   `breath/breathMax/lavaWet/hpPercent`，下一步要每步检查并在 hp<70% 就撤。
3. **向下盲挖**：竖井直通未探索洞穴，容易掉进水里或撞上怪。安全做法是沿**已有洞穴**走，
   或挖缓坡平巷，并且前方半径 6 格有液体就停。

结论：地下推进改为"先照明、先探水、每步看血、随时能魔镜撤离"，并优先做**地表/浅层**
能见度高的目标（如夜间打恶魔眼集晶状体）。

### 第 13 轮：基地布局的设计缺陷（必须重做）

现状诊断（逐格回读）：

- **一号房**：内部门对着一号房右墙外侧的**二号房左墙**，等于开出去撞墙；唯一可用的出口是后补的
  **左墙外门 (2092,304)**（验证可正常进出）。
- **二号房**：门通走道，但走道**从外部无法到达**（两侧都是房子，上方 7 格高）。
- **三号房**：被破坏严重——**整层地板 (y=305, 14 格) 全缺**、左墙 302..304 三格空缺（门也没了），
  只剩一个火把；`roomFound=false`，所以还有 1 个 NPC 没房。
- 结果：基地是个**迷宫**，人只能在房子之间穿行，无法从外部进入走道或三号房。

根因：房间**背靠背**贴着建，门又开在贴邻居的那一面；通道一开始就没留。

重做方案（下一轮）：

1. 每栋房子**只在自己外墙开门**（朝外空地），不再有"门对着邻居墙"。
2. 相邻建筑之间留 **3 格走道**，走道两端**通向外部**（不封闭）。
3. 每栋房子外墙各留 1 个**屋顶平台**入口（可从上面跳下），作为代理的备用通道。
4. 三号房先补地板（14 格 @y=305）+ 左墙门，让它重新合格，安顿那位无家 NPC。
5. 矿道入口单独建在**离所有房子 ≥15 格**的空地上，先插火把再往下，缓坡不竖井。

```
row3 309 -> 310.7
row4 310 -> 311.7     每行稳定下 1 格
```

铺绳：从**井底往上**铺，`place type:366`，8/8 全部成功（井道 2 格宽，
绳子贴着井壁所以有支撑）。

## A* 执行器的两个真 bug（这轮修掉，都已实测）

### 1. 往下挖只挖一列 → 永远下不去

`TickPath` 的 `dy >= 1` 分支原来只有：
```csharp
if (PathAllowDig && !TileAir(px, py + 2)) WalkMine(px, py + 2);
```
角色碰撞盒占 `px-1` 和 `px` 两格，只挖 `px` 会在脚下留一格实心，
结果就是**原地上下跳、一格都下不去**——之前"跳 60 秒"的真因不是没路，是少挖一列。
修好后实测：y 302.7 → 305.7 → 307.4 → **311.7**（一口气挖下去 9 格）。

### 2. 看门狗用坐标判据 → 抖动时永不触发

第一版写的是"整数 px/py 连续 45 帧不变就停"，但人在原地抖 1 格时
py 会在 305/306 之间来回变，计数器每帧被清零，**60 秒都不会停**。
改成**路径下标不再前进**当判据：
```csharp
if (PathIndex == PathLastIndex) PathIdxStuck++;
else { PathIdxStuck = 0; PathLastIndex = PathIndex; }
if (PathIdxStuck > 90) { StopPath("no-progress"); return; }
```
实测：卡住后约 3 秒返回 `stop:"no-progress"`，`active:false`，不再干等。

### 3. 部署链的坑：改仓库不等于改游戏

`cycle.ps1` 原来只编译 `ModSources\DshTerrariaBridge`，而代码在 git 仓库里，
所以**改仓库 + 重启 = 装的还是旧代码**（这轮白测了一次，`.tmod` 三次都是 95376 字节）。
现在 cycle.ps1 在编译前自动 `仓库 -> ModSources` 同步（通配符定位仓库路径，
不写中文字面量：PowerShell 5.1 读无 BOM 文件时会把中文路径读坏，导致同步静默跳过）。
同步后 `.tmod` 变成 95608/95610 字节，才是真的新代码。

### 竖井下探 + 主动插火把（新世界·沙漠地表往下）

- 用户点出的两个干扰先清掉：自动打怪默认关（`guardDefault=false`，`swings=0`）、换世界/死亡
  `ResetMotion()` 清空全部行进状态（`latched` 十项全 false）。站桩 2.5 秒坐标不动，速度 0。
- 走路回归：`move right` 600ms 位移 6.8 格（≈11.3 格/秒），松手后位置不再变化。
- 背包曾经 0 空位（挖到的东西静默失败），丢掉 11 格垃圾（脚镣/旗子/墓碑/僵尸臂）后剩 11 空位。
- 下挖从地表一直挖到地下土层，每 5 层插一根火把；`find type:4` 在竖井范围内回读到 8 根。

### 走路重构 + 自建房跨越 + 三条硬规则（2026-10-26/27）

这一轮的主线是「把走路从一堆互相抢 `return` 的 `if` 改成三层」，副产品是一批真 bug
和一批用户当场纠正的规则。全部有回读证据。

**走路三层落地**（详见 `docs/walk-rework-plan.md` 第四节）

- `TickWalk` 拆成 `SenseWorld` / `ActorDecide` / `ActActor`：感知层每 tick 扫 8 列地面，
  算出落差、墙高、是否建材、是否门、是否坑；决策层按优先级出一条例；执行层只写
  `controlLeft/Right/Jump`。
- 这一步的真正收益不是"能走更远"，而是**改一处不会再坏三处**：以前 9/11/12/13 四条
  "前方有障碍"的判定各自能 `StopWalk`，调一个阈值就跟另一个打架。

**平台不是空气、也不是实心**

`TileSolid` 只查 `Main.tileSolid`，平台（tile 19）在里面是 `false`，于是被当成可穿过的空气；
人一走到平台上就掉下去，A* 也把平台当成坑。新增 `TileStand()`（实心 **或** 平台）后，
地面判定全部改用它 —— `walkto` 从"走 11 格"直接提到"走 68 格"。

**门：走过去它自己会开，不要挥镐**

以前走到门口就判"前方是建材"→ 重新规划 → 无路可选 → 停下。正确做法是**放开门的控制、
让原版自己开**（用户纠正："这是你自己之前做的 NPC 的房子"、"你进入了房子走到了最右边
被墙挡住了"）。现在 `open-door` 走 `BeginTileInteraction` 的真实右键输入，
不挖不炸，门状态必须回读确认。

**自建房的出口设计**（写进 `docs/kb/build-standard.md`）

优先级：走门 → 屋顶连续留 1~2 格平台（能从下方跳穿、也能按下落穿，人和 NPC 都能过，
且仍算天花板）→ 从外侧落脚点翻出去 → 最后才考虑动墙。
另外一条判据：「这堵墙是不是我造的」**不能只看方块类型** —— 自建房的材料就是普通土石，
和天然地形一模一样，只能靠建造方自己登记"已建结构"。

**顺手纠正的两条错知识**

- `build-standard.md` 原来写"不要用平台做墙或屋顶，判定必然失败"—— 实测错。平台能当屋顶，
  只是平台那几格不计入房间内部空气，本来刚好达标的房可能因此掉到线下。

  **按满 6.1 格**。`jump` 的默认时长随之从 150ms 改成 400ms —— 之前用 3.8 格去试 4~6 格的
  平台，试几次就断言"跳不过去"。

**三条规则写进 `AGENTS.md`**

1. §0.5 **工作循环**：接任务 → 执行 → 遇困难 → 自己判断 → 用已有基础能力解决 → 推进。

3. §0 **重启游戏必须先得到用户允许**：部署脚本的默认流程是杀进程→编译→启动，

## 第 193 轮：清掉 7 条假缺口，并给"声明过期"加了自动反查

### 现象

`npm run tc:dry` 报 **49/58 通过、9 条缺口**，看上去知识库和动作原语都缺一大片。
逐条打开核对，只有 2 条是真的——其余 7 条是**用例声明没跟上实现**：库或命令早就有了，
`needs.kbMissing` / `needs.unsupported` 还留着。

### 离线预检到底判什么

`src/testcases.js` 的 `precheck` 只看三件事，三者全空才算 PASS：

1. `needs.commands` 里的命令在不在 `capabilities.json`（不在 → 动作原语缺口）；
2. `needs.unsupported` 是否非空（非空 → 撞上"明确做不到"，能力缺口）；
3. `needs.kbMissing` 是否非空（非空 → 知识缺口）。

所以它读的是**用例自己的声明**，不是现实。声明一旦过期，预检就把"能做"报成"做不到"，
缺口清单跟着假，后面照着假清单去补库、去加命令，做的都是无用功。

### 逐条核对结果

| 用例 | 声明说缺什么 | 现实 |
|---|---|---|
| M07 大地图 | 没有大地图读取能力 | `map` 命令在 `Commands.cs` 与 `capabilities.json` 都有；`world_biome` 写了「地图与我到过哪」 |
| K06 拆分堆叠 | 没有拆分规则 | `item-operation.md` §堆叠拆分与合并：拆出量夹在 1..总数-1、进第一个空格、背包满必失败 |
| F01 钓鱼 | 没有钓鱼流程 | `loot-source.md` §钓鱼 + `castline`/`bobber`/`reel` 三条原语都在 |
| F02 捉虫 | 没有捕捉机制 | `loot-source.md` §捉虫 + `capture`（who 或坐标） |
| N04 / F04 渔夫任务 | 没有渔夫任务 | `npc-town.md:79-83`：每日任务、`quest` 回包字段、交付走 talk |
| E01 / E05 血月 / 入侵 | 没有随机事件能力 | `startevent` 触发（测试入口）+ `event` 读状态 + `guard`/`attack`/`heal` 守夜 |

### 真缺的那点东西，补进库

- **M06 微光池**：`world_biome` 新增「微光池（以太）在哪」。位置不是随机的——世界外侧五分之一、
  地下层或洞穴层（地狱之上）、**永远和丛林同侧**、只生成一个、中心是一池微光液体，
  微光图格达数百格量级才判定为以太群系。正确找法：认丛林侧 → 往那侧外围 → 下到地下/洞穴层 → 横向扫；
  靠"随机往下挖"命中率极低。
- **F02 捉虫**：`loot_source` 补全判定细节——虫网是工具、空挥不消耗，判定距离和短兵器相当，
  目标会飘会跳所以要"等它进入范围那一下挥"，只有小动物能进网（敌怪/NPC/宠物/Boss 一律拒绝），
  抓到是物品直接进背包，任务鱼是钓的不是网的。

### 结果是

`npm run tc:check` 结构无提示；`npm run tc:dry` **56/58 通过、2 条缺口**（N04、F04，都卡在
"渔夫任务交付要点击对话选项"这同一处，没有原语）。

### 顺手加的反查（这一轮真正的产出）

原来的 `validate()` 只对 `missingCommands` 做反向检查——"声明缺的命令其实已经实现了就报警"。
`kbMissing` 没有对应的检查，这就是 7 条假缺口能躺这么久的原因。

现在用例可以带 `needs.kbMissingProbes: [{ text, keywords }]`：`text` 必须逐字出现在
`kbMissing` 里（不同步就报 error），而 `keywords` 全部出现在 `needs.kb` 对应的库全文里时
报 warning「知识已入库（… 都在），把 kbMissing 里的「…」删掉」。

配套 `test/kb-missing-probe.test.js` 4 条：能抓到残留声明、探针与声明不同步按错误处理、
真实用例库这类警告必须保持 0 条、以及**每条 kbMissing 必须配探针**（不许再靠人肉核对）。

教训写进这一条：**判据要能自己变红**。加诊断、加声明、加"缺什么"的清单，都要配一条会在
现实变化后自动报警的检查，否则清单会静默腐化成假账。

## 第 194 轮：进游戏实测 87 条命令，修掉 4 个 bug

**现象**：上一轮的 NPC 社交改动（`bf2996c`/`e8b8f5b`）只做过单机验证，`fly`、`path`、

**第一个发现比任何命令都重要**：单人模式一失焦 `paused` 就是 true，`applyInput` 被跳过，

`paused:false` 与 `hasFocus:false` 能同时成立——服务端在跑、客户端只发输入，
于是**不抢窗口也能让角色真的动**。这条改变了整个测试的可行性（此前只能在用户坐在

### 修掉的 4 个 bug

1. **`fly` 完全不动**。连试 5 次全部 `velY:0`、翅膀 180/180、位置一格不移。
   根因是 `Fly` 只写了 `JumpUntil`/`JumpIssued`，**漏了 `IntentJump = true`**；
   而 `BridgeSystem.cs:616` 是
   `player.controlJump |= IntentJump || (triggers.Jump && JumpUntil > now);`
   ——没有 `IntentJump` 就只剩真实物理按键，这套环境没有按键，`controlJump` 恒 false。
   同文件 `BridgeSystem.cs:614-615` 给 up/down 写的时候已经注释过"不能躲在 triggers 后面"，
   jump 这行没跟上。改成调 `BridgeSystem.BeginJump(...)`（它本来就有三行）。
   `unhook` 里那句"松手后跳一下"同病同修。
2. **`accessory` 不带参数就卸装备**。`Json.Bool(p,"off",true)` 默认 true，
   实测里一次 `accessory {}` 卸掉冰冻护盾、一次 `accessory {from:26}` 又卸掉烈火手套
   （`from` 被忽略，因为先走 off 分支）。两次都已装回原位。
   改成默认只读列清单，卸下必须显式 `off:true`。
3. **`shop {npc}` 中文名解析不出商店**。`GetShopName` 返回的第三段是本地化 NPC 名

   另外 `shop {shopId:38}` 会 `Index was outside the bounds of the array`——
   商店 id ≠ NPC 类型，`SetupShop` 外面包了 try/catch 给友好提示。
4. **关不掉对话**。`interact` 点空地两次都无效，桥里从来没有关对话的入口。
   用 `api` 查到 `Main.CloseNPCChatOrSign()` 是 public static，包成只读命令 `talkclose`。

`Main.OpenShop(Int32)`、`Main.CloseNPCChatOrSign()`、`Main.SetNPCShopIndex(Int32)`、

## 第 194 轮（续）：打包三次才把「改了的代码」真的送进游戏

### 现象

`fly` / `accessory` / `shop` / `talkclose` / `talk` 五处改完、`npm test` 全绿、`dotnet build` 0 错误，
打包也报 `Packaging: DshTerrariaBridge` —— 进游戏一测，`fly` 还是**一格不动**，
`talk` 报的还是旧文案「太远（61 格）」而不是新的「离 … 太远（61.0 格），原版对话判定约 5 格内」。

### 根因：三次"以为生效了"

1. **第一次（14:38）**：打包用的是 `bin/Release/net8.0/*.dll`，那是 **14:30:28** 的产物；
   而 `talk` 的改动是 14:30 之后写的。`-eac` 只负责把已有的 dll 塞进 tmod，它不负责先编译。
   **铁律：改完源码先 `dotnet build -c Release --no-incremental`，再 `-eac`。**
2. **第二次（15:10）**：dll 新了，`talk` ×`5` 格和视线检查都验到了，`shop` 中文名解析也通了，
   但 `fly` 仍然不动 —— 说明 **`BeginJump` 里的 `IntentJump` 不是唯一的坑**。
3. **第三次（15:51）**：加 `StopAutomatedMovement("manual-fly")`，`fly` 才真的能升 **+22 格 / +13 格**。

### 为什么是这一句

`ApplyMovement`（`BridgeSystem.cs:1990`）开头 `if (MovementAppliedTick == Now) return;`，
之后按 `ExactActive`(2005) → `PathActive`(2071) → `WalkActive`(2072) → `FollowActive`(2089)

## 第 195 轮：清单里 16 个命令名根本调不通（生成器的盲区）

### 现象

真机复测 `talkoption` 时顺手敲了 `bloodmoon`，回来的是：

```
Error: unknown command: bloodmoon（可用：accessory/api/attack/blood/bloodmoon/…）
```

**同一条错误信息里，"不可用"的那个名字正躺在"可用"清单里。** `right` / `left` 也一样。

### 查证

写脚本比对 `DshTerrariaBridge/Commands.cs:495` 的 `CommandNames` 数组与顶层 `switch (cmd)` 的 `case`：

```
顶层 case 91 个；CommandNames 97 个
列表有 / 顶层 case 无（16）：blood bloodmoon eclipse frost frostmoon goblin martian
                             pirate pumpkin pumpkinmoon snowman snowmoon left right up down
```

16 个分两批，来路完全不同：

- `left/right/up/down` → `move` 的 `dir` 取值（`Commands.cs:3317-3320` 的内层 switch）；
- 其余 12 个 → `startevent` 的 `event` 取值（`Commands.cs:4529-4549` 的内层 switch）。

`scripts/kb-caps.mjs:339` 和 `scripts/kb-sync.mjs:86` 都是**全文扫 `case "xxx":`**，于是参数值冒充了命令名，
一路虚高到 capabilities.json / capabilities-manifest.md / _generated-commands.md / AGENTS.md 的能力块：
**111 条命令，实际 91 条。**

### 修法

1. `CommandNames` 删掉这 16 个 → 91 个，与顶层 case 双向差异为空；
2. 两个生成器都改成：先 `findIndex(/switch\s*\(\s*cmd\s*\)/)` 定位命令入口，再用 `braceDelta` 配平出
   这个 switch 的行范围，**只在该范围内扫 case**；
3. 重跑 → `91 commands`；`npm test` 330 tests / 328 pass / 0 fail / 2 skip；`npm run tc:dry` 56/58 不变。

### 为什么能瞒这么久

`npm test` 里关于生成物的测试问的是"**生成物是否等于生成器的输出**"。生成器和生成物一起错，
两边一致，测试就绿。**它从来没有问过"清单里每个名字都能调通吗"。**

这和 193 轮那次"用例库虚报缺口"是同一个形状的毛病：**判据只在一个方向上闭合**。
上次是"声明的缺口是否还在"没有反查，这次是"声明的命令是否真能调"没有反查。
两次都是靠**反向问一句**才暴露，不是靠跑测试。

### 第 195 轮（续）：不带参数的三次事故

修完幽灵命令名，继续把剩下没测过的命令逐条敲一遍。三次都是"少传一个参数"造成的：

| 命令 | 少传什么 | 出了什么事 | 根因 | 修法 |
|---|---|---|---|---|
| `shopdebug` | （什么都没缺） | `Error: Index was outside the bounds of the array.` —— 一句英文异常直接泄出来 | `Main.SetNPCShopIndex(npc.type)` 传的是 **NPC 类型**（228），该 API 要的是**商店 id**；`Main.instance.shop` 只有 2 个槽 | 先用 `ResolveVanillaShopIndex` 解析 shopId、解析不到明确报错、数组加空值保护、返回里补 `shopId`/`shopName` |
| `trash` | `count` | 一次销毁 **2081 个火把** | `count` 默认 `it.stack` | 默认改 `1` |
| `travel` | `dir` / `distance` / `dig` | 默认 `right` + `100` + `dig:true`，在出生点旁**挖 10 格、挥 12 下、走 106 格** | 出生点保护写的是 `if (dig && dir == "down")`，水平方向根本没挡 | 改成"起点或终点任一在出生点 100 格内就拒绝 dig" |
