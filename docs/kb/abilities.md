# 能力、移动 profile 与动作失效

本库描述“角色当前能做什么”以及动作规划怎样使用这些信息。它只写换任何世界和存档都成立的规则，不记录某个角色的装备数值、单局测量结果或固定动作时长。

## 能力、当前状态与连续 profile

三类信息必须分开：

- **能力**是动作门槛。它回答“当前是否具备某种能力”，例如能否飞行、二段跳、冲刺、抓钩、水上行走或免疫摔伤。
- **当前状态**是能力此刻是否能用，例如飞行剩余时间、二段跳是否已经用掉、冲刺是否冷却、是否湿身、是否被蛛网或冻结。
- **连续 profile**描述动作的范围和手感，例如最大速度、加速度、减速度、跳跃水平距离和飞行持续能力。

装备名称是原始诊断线索，不是规划接口。规划优先使用当前生效的派生能力，例如 `doubleJumpAvailable`、`canDash`、`canWalkOnWater` 和 `immuneFallDamage`，这样不同装备和增益可以映射到同一套动作规则。

## 能力门槛

### 飞行、跳跃与冲刺

普通跳跃、二段跳、翅膀飞行和飞行坐骑是不同能力。持续按跳键的含义会随能力变化：没有翅膀时可能只是一次跳跃，有翅膀时可能继续进入飞行。动作规划必须读取当前能力和剩余资源，不能把“按住跳”当成固定高度函数。

跳墙或跨坑前应检查跳跃能力、可用的二段跳状态、空中水平控制和落点空间。跳跃 profile 只能估计可达性；实际执行仍要按位置、速度、上升或下降状态闭环停止。

### 抓钩、坐骑与绳索

抓钩能力包括是否装备抓钩、抓钩类型、射程、可同时存在的钩数和当前是否已经挂住。坐骑能力包括当前坐骑、是否飞行、是否改变水平控制和是否改变碰撞边界。

绳索动作还依赖脚底绳格、身体是否接触绳、引擎的攀爬状态和输入是否真的进入原版控制位。仅有 `pulley` 或仅有输入标志都不能单独证明爬绳成功，必须回读位置变化和绳索接触。

### 液体、坠落与环境阻断

水上行走、岩浆行走、火块免疫和摔伤免疫是不同能力。规划时要同时看能力和环境类型；拥有水上行走不等于能在岩浆上行走，也不等于不会溺水。

`wet`、`lavaWet`、`honeyWet`、呼吸、重力方向、蛛网、冻结、石化和混乱状态属于当前状态。它们可能暂时阻断动作，即使装备能力没有变化，也必须触发停步、脱险或重新规划。

### 感知与照明

生物探测、危险探测、宝藏探测和照明是感知能力，不应混成移动能力。规划器可以用它们决定是否扩大观察范围、是否避开未知区域，但感知字段不能代替实际的地形和敌怪回读。

## 动作执行分工

### 闭环动作

只要动作结果能被稳定观察，就优先发出真实输入并轮询结果：移动到位置、挖掉方块、放置方块、使用物品、跳到可观察高度和脱离危险区域都属于这一类。

闭环必须有目标条件、停止条件、超时或卡住条件和危险中止条件。达到目标后松开输入并回读最终状态；位置不变、速度异常为零、生命或呼吸恶化时，应停止并重新判断原因。

### 可达性与标定

标定用于回答“这条边能不能通过”，而不是替代动作执行。跳墙、跨坑、落差、飞行续航、抓钩射程和需要预估风险的路径边可以使用分档 profile 或小规模探测。

标定结果必须带有适用条件和可信度。装备、增益、坐骑、重力或液体状态改变时，只使依赖这些条件的动作族失效，不要把一次变化扩大成全局重标。

### 诊断与异常检测

连续字段默认用于初始预算、超时保护和异常检测，不作为动作成功的唯一判据。真正的成功判据仍是位置、瓦片、物品数量、生命、弹幕或其他引擎状态的变化。

例如 `maxRunSpeed` 变化可以调整移动分段和超时；只要 `moveto` 仍然按位置闭环，就不必因为速度变化重建所有路径。若速度变化让某个跨坑边从可达变为不可达，则必须使该跳跃动作族重新评估。

## 失效与重标

每个动作族都应声明自己的依赖：能力门槛、当前状态、连续 profile、地形条件和观测字段。

- 能力门槛变化时，立即使依赖它的动作族和可达性边失效。
- 连续 profile 变化时，只更新受影响的预算、停止条件或可达性边。
- 当前状态短暂变化时，暂停或改变当前动作，不自动生成新的永久标定。
- 单次失败先按地形、焦点、输入时机和资源检查；在相同条件下重复出现行为偏差，才把 profile 标成过期并重新标定。

“是否重标”的判据是后果：变化是否会改变动作能否完成、是否安全、何时停止或异常检测是否可信，而不是数值差达到某个固定百分比。

## 运行时资料分层

- `docs/kb/abilities.md` 保存通用机制、字段含义、动作依赖和失效规则。
- `NavRules` 保存导航政策，例如风险阈值、容差、重试预算和标定结果的保守使用方式。
- `MobilityProfile` 保存当前角色、装备、增益和状态下的连续移动参数与跳跃可达性表，并记录适用条件和可信度。

`MobilityProfile` 可以热更新；它不应被伪装成静态知识库，也不应把某个存档的数值写进通用规则库。

## 执行前检查

动作开始前至少确认：当前能力是否满足门槛、当前状态是否允许动作、环境是否有不可逆风险、动作结果是否可观测，以及失败后是否有安全退路。任何一项不满足，都应先补状态读取、改走可达性判断或停止执行。

## 坐骑快捷召唤：为什么必须走输入层，不能写 Player.controlMount

2026-10-29 实证。`controlMount` 这个字段和 `controlLeft/Right/Up/Down/Jump` 不是一类。

反编译 `tModLoader.dll` 的 `Player.Update` 行号顺序：

```
23673  ResetControls()                     ← 清空所有 control*
23674  if (Main.hasFocus) {
23678      PlayerInput.Triggers.Current.CopyInto(this)   ← 输入层复制进 control*
23783      if (controlMount) { if (releaseMount) QuickMount(); }
23960  PlayerLoader.SetControls(...)      ← mod 的 SetControls 钩子在这里
24956  PostUpdateMiscEffects(...)         ← 更晚
26297  QuickGrapple()                     ← 抓钩读点
```

**结论一**：`controlMount` 的唯一读点（23783）比 mod 能拿到的每一个写入点（23960、24956）都早。
所以无论写在 `SetControls` 还是 `PostUpdateMiscEffects`，都活不到 23783 那一行 ——
实测 `DbgPrePhysicsMount` 读到 `true`，`mounted` 却始终 `false`。

**结论二**：抓钩能用是因为它的读点（26297）在写入点之后。两者位置不同，不能套用同一个写法。

**结论三**：唯一有效写法是写输入层，让 23678 的 `CopyInto` 把它带进 `controlMount`：

```csharp
ApplyBridgeTrigger(MountUntil > now, ref BridgeMountHeld,
    t => t.QuickMount = true, t => t.QuickMount = true, t => t.QuickMount = true);
```

改后实测：骑上（`mounted true`、`mountType 7`）、再按一次下骑，连续 3 轮 3/3 稳定。

**判据**：一个控制位该写在哪，取决于它的读点在 `Player.Update` 里有多早 —— 早于 23678
就必须写输入层（`TriggersSet`）；晚于 24956 才能直接写 `Player.control*`。
