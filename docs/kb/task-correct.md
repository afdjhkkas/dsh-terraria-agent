# 对话理解与任务纠错知识库（task_correct）

> **只写"怎么理解指令、怎么在不确定时处理"的通用逻辑**，与地图和具体任务无关。

---

## 1. 模糊指令处理规则

- **先做最小可用方案**：玩家说"把家弄一下"，就先让房子"合格 + 能住"，不擅自加装饰、不加塔楼。
- **不擅自扩大范围**：只动被点到的区域；要动别处先问。
- **不追加额外复杂结构**：能用一个火把解决的事，不砌一座灯塔。
- **保守执行**：不确定的地方停住、问清楚，不要靠猜往下推进。
- **默认值要能解释**：为什么选这个做法、依据哪条规则，说出来。

## 2. 歧义处理规则

- **一条指令多个意图时，先做主语**：例如"修好房子再让 NPC 住进去"，先保证房子合格。
- **不擅自附带次要需求**：次要需求列出来问，不默认执行。
- **名字指代不明**（"那个箱子""那个 NPC"）→ 先报出候选，让玩家选。
- **数量不明**（"多挖点"）→ 给一个具体数量并确认。
- **时间不明**（"等一下再弄"）→ 问多久，或者先做别的。

## 3. 任务中断规则

- **缺少必要物品 → 停下来报缺口**：缺什么、缺多少、哪里能拿到。
- **地形条件不满足 → 停下来报原因**：例如"这里放不下多格家具，因为上方没有净空"。
- **违反游戏机制 → 直接说做不到**，不要编一个看起来合理的假方案。
- **多条需求互相冲突 → 让玩家定优先级**，例如"先存东西还是先继续挖"。
- **被玩家打断/撤销 → 立刻停手**，不要"把这一步做完再说"。
- **连续失败两次就换策略**：第三次还按同样方式做，只会浪费时间和材料。

## 4. 修改迭代规则

- **只改目标区域**：不动已完成的部分，不做整体推倒重建。
- **改之前先拍现状**：位置、尺寸、已经有什么，先读一遍再动手。
- **改动要可回退**：记下改了哪几格，出问题能补回去。
- **玩家说"不对" → 先复述他的意思，再动手**：改错方向比改慢更糟。
- **一次只改一处**：改完立刻验证，再改下一处。
- **报告用事实**：改了几格、现在什么样、哪里还没好；不用"应该可以了"这种话。

## 5. 无法完成时怎么回

- **说清楚卡在哪一环**：缺物品 / 缺条件 / 机制不允许 / 需要玩家先做一步。
- **给可行的替代路径**：例如"直接搬不行，但可以先修好空房，再让 NPC 自己选"。
- **给出需要玩家做什么**：点一下菜单、给个材料、换个位置。
- **不要把"没验证"说成"已完成"**：没读到结果就说明没读到。
- **不要把失败包装成成功**：宁可说"这一步失败了，原因是……"。
## 3. 卡住时的第一反应：先检测判断，不要改代码

**这是本项目最贵的一条教训：同一个"走路卡住"的现象，我改了十几个小时的代码，而它用现成命令两步就过了。**

### 正确顺序（必须先走完这三步才允许动代码）

1. **读地形**：`scan` / `tile` 把脚下、身体、头顶各若干格的类型读出来，先看清是台阶、门、平台、实心墙、还是坑。
2. **在现有命令里找解**：`move`（走）、`jump {ms:N}`（原生按住跳跃）、`use`（使用物品）、`interact`（右键交互）、`place`（垫方块）、`hook`（抓钩）。绝大多数障碍靠这几条就能过。
3. **确认是能力缺失再说**：只有"现有命令确实表达不了这个动作"时，才改代码；改之前先说出"缺的是哪个动作、为什么现有命令做不到"。

### 反例记录（都是真实发生的）

- 走路卡在自建房右墙前 → 我改寻路四类边、改包络、改到达阈值、改注入时机，部署重启十几次。
  实际解法：使用原生 `jump {ms:400}`，等回读确认身体越过屋顶后再 `move` 横移。
- 判断"跳不上去" → 我以为是命令退化，去改跳跃注入点（还写了个框架里不存在的钩子名，编译直接失败）。
  实际原因：头顶有平台/木块时，原版跳跃高度会受碰撞和站位影响；应调整站位或合法搭建落脚点，不能直接给定初速。
- 往返两趟跨两间房，全程只用 `move` / `jump`，没有一行代码改动。

### 判断"是不是该改代码"的一句话标准

**能用现有命令组合表达出来的动作，不许改代码；改代码只在"动作本身不存在"时才允许。**

### 部署的代价

每次改代码都要重新编译 + 重启游戏（数分钟，且会把玩家从当前位置送回出生点、回滚未落盘的进度）。
所以"改代码"不是零成本动作，它本身就破坏正在进行的实验。**先在游戏里试，再决定改不改。**

## 4. 通用工作模型：检测 → 判断 → 调用基础能力 → 再检测

**这是做任何一件事的唯一姿势，不分任务大小。**

```
     ┌──────────────────────────────────────────────┐
     │  1. 检测现状（读，不写）                      │
     │  2. 判断"现在缺什么 / 下一步做什么"            │
     │  3. 调用一个基础能力去做（原子动作）            │
     │  4. 回读确认这一步真的发生了                   │
     └──────────────► 回到 1（直到目标达成）────────┘
```

### 什么是"基础能力"

只包括**原子动作**，不包括"自动完成某类任务"的脚本：

`移动` `跳跃` `挖掘` `放置` `使用物品` `交互` `攻击` `抓钩` `合成` `丢弃` …

**严禁**写"遇到障碍物就自动挖掘"这类把判断烧死在代码里的脚本 —— 那等于取消了判断。

### 用这个模型做例子：盖一间 NPC 房

| 步骤 | 检测 | 判断 | 动作 |
|---|---|---|---|
| 1 | 扫一遍周围地形：哪里平、哪里有树/草/杂物 | 这块不能直接盖，要先清 | 挖掉/砍掉挡路的 |
| 2 | 再扫：地面这条线连续吗、上面有空间吗 | 地面不平 / 高度不够 | 补平、清高 |
| 3 | 量一下可用空间（宽、高） | 够不够一间房（宽十格以上、高五格以上） | 不够就继续清 |
| 4 | 地板有了 | 还缺墙 | 两侧立墙 |
| 5 | 墙有了 | 还缺天花板 | 封顶 |
| 6 | 壳有了 | 还缺门、椅子、光源、工作台 | 逐个放 |
| 7 | 都放了 | 还合不合格？ | 用房屋判定查一次 |
| 8 | 合格 | 还缺 NPC | 等 NPC 入住 / 去请 |

**清理过程中同样会出问题**（树挡着、坑太深、挖到水），那就回到第 1 步重新检测、重新判断 —— 不是去改挖掘逻辑。

### 判断必须有依据

每条判断都要能说出依据（"宽只有 8 格，房判要求 10 格以上"），
而不是"感觉差不多了"。依据来自知识库，不来自直觉。

### 和"写脚本"的区别

- **脚本**：把"如果前方有障碍 → 挖"这种判断固化成代码，一次写死，换场景就错。
- **这个模型**：判断发生在**每一步的现场**，依据每次都重新读，场景变了判断自然变。

一句话：**代码只提供"手"，判断永远由操作者现场做。**
