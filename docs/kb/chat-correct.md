# 对话与纠错库（chat_correct）

> 只在"玩家说得模糊 / 我失败了怎么回 / 我被纠正了"时加载。
> 核心：**先对齐意图，再动手；失败要说清失败在哪一格，不粉饰。**

## 1. 玩家模糊请求处理策略

| 玩家说的 | 真实意图（大概率） | 先做什么 |
|---|---|---|
| 「把家完善一下」 | 修结构 + 让它能住人 | 先 `scan`/`tile` 看清现状，列出"缺什么"再动手 |
| 「搞点装备」 | 挖矿→熔炼→锻造 | 先 `inventory`+`recipes` 看缺什么，再定路线 |
| 「你自己看着办」 | 授权自主推进 | 挑**最小可验证**的一步做，做完汇报证据 |
| 「去打 Boss」 | 需要准备（装备/场地/药水） | 先报准备缺口，不要直接冲 |
| 只有地名/方位 | 要赶路 | 先确认目的地坐标或特征 |

规则：
- **不超过一个问题**；能靠 `state`/`scan`/`inventory` 自己查到的，不要问。
- 模糊但风险低 → 先做最保守的一步，边做边报。
- 模糊且风险高（拆房、挖穿水层、花光材料）→ 先确认。

## 2. 指令执行失败话术

必须包含三件事：**做了什么 → 卡在哪（具体坐标/报错原文）→ 下一步打算**。

✅ 好例子：
> 屋顶补到 (2121..2126, y298) 6 格都回读到 WoodBlock；但 `homeroom` 报
> 「(2112,301) 不是一个房间」，商人还在 (2099,402)。查出来是我 `roomcheck`
> 里 `CheckRoom(0,1)` 传错参数，判定链路本身是坏的 —— 先把检测修对再补房子。

❌ 坏例子（都说不得）：
- 「已完成」「应该可以了」——没有回读证据。
- 「环境有问题」「工具坏了」——没定位到具体代码/坐标。
- 沉默重试 3 次然后换个话题。

## 3. 识别歧义的处理方式

1. 先复述意图（一句话）："你是想让我把西边那间屋子修到能让商人住进去，对吗？"
2. 给出 2 个以内的选项，带上代价："要么把西屋补成 60 格（约 30 块木头），要么重建一间 12×6。"
3. 不同时问两件事；不把选项写成作文。

## 4. 玩家纠错后的修正逻辑

用户纠正 = **最高优先级**，且要落成规则，不是当场改一次就算。

流程：
1. **复述**他的原话要点（确认没听错）。
2. **定位**：这条纠正对应哪条现有规则/哪段代码？之前的做法错在哪一步？
3. **改代码或改文档**：能固化成检查的写成代码；不能的写进 `AGENTS.md` / `docs/progression-plan.md`。
4. **复测**：用这次场景重跑一遍，给出回读证据。
5. 报告时写"之前错在 X，现在改成 Y，证据是 Z"。

已固化的几条（例子）：
- 「用指令在后台控制角色，而不是直接控制我的电脑或用指令改变世界」→ AGENTS.md §0
- 「不要写一键建造的脚本」→ 只用 place/mine/craft 这类基础能力
- 「黑的地方要插火把」「打仗前掏武器」「别在出生点下挖」→ 行为规则

## 5. 无法完成请求的回复规范

```
1. 直接说结论：做不到 / 现在做不到 / 需要先做 X
2. 原因（客观、可验证）：缺材料 / 缺前置能力 / 游戏机制不允许 / 环境不允许
3. 替代方案（1~2 个）
4. 需要他做什么（如果需要）
```

不要：
- 假成功（最严重）
- 把"没试过"说成"试过了"
- 用"我觉得""大概"替代实测

## 6. 汇报格式（默认）

```
做了什么：<动作 + 坐标>
证据：<回读到的值>
没做到：<哪一步 + 报错原文>
下一步：<一个具体动作>
```
短、可核对；一次不超过一屏。用户在看直播，别让他等长文。
