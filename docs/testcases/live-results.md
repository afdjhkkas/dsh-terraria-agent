阶段 1 是离线推演（`sim-packets.md` / `sim-gaps.md`），这里的每一条都是**在运行中的游戏里跑过并有回读证据**的。
判据统一：命令回 `ok` 不算过，必须读到世界/背包发生变化。

## 这一轮挖出来的真 bug

1. `find {type:0}` 永远返回空 —— 泥土（tile id 0）被当成"没填参数"，命令直接报错。已修：`type` 允许 0。
2. `inventory` 读不到背包空位 —— 只有物品列表，没有 `free`。已修：新增 `free` / `freeMain` / `freeAll`。
3. 斧头有效距离比镐短 —— 4.3 格外挥斧，游戏接受指令但格子不掉、木材不涨，看着像成功。已修：砍树单独用 4 格判定并明确回报"砍树要靠近"。
4. **镐能拆树但不掉木头** —— `Main.tileAxe[Trees]` 在这个版本是 false，工具选择据此挑了镐：树格消失、木材一点不涨。已修：把 `TileID.Sets.IsATreeTrunk` 与仙人掌并入砍伐判定（修后同一格 `mine` 自动选铁斧）。
5. **树干是多击物体** —— 铁斧要 4 击才断，单次 `mine` 看着“没反应”其实是伤害在累积；循环调用到回读 `type != 5` 才算砍下。
6. `place` 返回的 `placed` 字段恒为 false（它只是"挥动已排入"）—— 用它判成功必然误判。以 `terraria_place`（会轮询回读）或自己 `tile` 回读为唯一判据。

## 这一轮确认的两条游戏规则

- **门要过梁**：1 宽 3 高的净空之外，上方紧贴的一格必须是实心方块，否则放置被静默拒绝（旧档连试 8 次全败的真因）。
- **家具要落在普通物块上**：墓碑、工作台、平台这类框架物块不能当支撑面；放上去同样静默失败。

### 第三轮挖出来的真 bug / 真规则

1. **镐能拆树但不给材料**（已修，见上）。
2. **砍树要多击**：铁斧 4 击断一棵普通树；只挥一次就下“砍不动”的结论是错的。

4. **合成站有距离限制**：离工作台 6 格时报“附近没有这个配方需要的工作站”，
   站到 2 格内立刻成功；跳上树顶（纵向离开 6 格）同样算够不到。

### 第四轮确认的三条硬规则

1. **竖井下掘的目标行不是 `py+2`，而是 `floor(py+1.35)`**：角色中心到脚底约 1.3 格，挖 `py+2` 只会挖到脚底下面那一层，人不会掉；必须把“脚底所在行 + 下一行”各两列共 4 格都挖掉，人才会掉一格。
2. **合成站有作用距离**：同一个人物，站在出生点（离工作台 25 格）`craft 熔炉` 直接报“附近没有这个配方需要的工作站”，走到 x≈2120（离工作台 2 格）同一命令立刻成功。→ 合成前先靠近工作站，别在远处下命令。
3. **容器是双向的**：`chest` 既能 `deposit` 也能 `take`，两边都以物品堆为单位（整堆移动），回读以箱子物品数与背包格内容为准。

## 第五轮真机（K03 熔炼闭环）

| 用例 | 结论 | 证据 |
|---|---|---|
| K03 熔炼一次得金属锭 | **PASS** | `find type:166` 在 (2070,290)/(2071,289)/(2071,290) 找到锡矿 3 格 → 两列出竖井下到 y287.7 → 逐格挖到回读为 air → 自动入包 `锡矿 x3` → 魔镜回出生点 → 走到 (2116.5,275.7) 熔炉旁 `craft {item:703}` → `{"name":"锡锭","crafted":1}`，背包 `锡锭 x1` |

### 第五轮确认的四条硬规则

1. **`mine` 的时长要够，否则“命令成功、方块没破”**：同一格连续 3 次 `mine ms:1600` 才稳定清掉石头；`ms:1200` 时会出现“回读还是原方块”的假成功。判据必须是**回读 `hasTile === false`**，不是命令返回 `ok`。
2. **`minechain` 不是桥命令**，它只是 JS 工具层的组合；直接连桥时只能用 `mine` + `grab`（`grab` 半径为 8 格，超出就 `picked:0`）。
3. **掉落物会自动入包**：挖破后 `grab` 报 `picked:0, seen:0`，但背包已出现 `锡矿 x3` —— 判“挖到了”要看背包/世界状态，不能只看 `grab`。
4. **一宽通道会把角色卡死**：角色碰撞盒 1.25 格宽，只挖 1 列会卡在两列实心之间（`move` 四个方向全部无效、`jump` 也不动）。竖井/隧道一律挖 **2 列以上**，卡住时的解法是**把身边那一列再挖开**，不是反复 `move`。


## 第六轮真机（S7 存盘 + 房屋复检 + 落盘验证）

| 用例 | 结论 | 证据 |
|---|---|---|
| S7 世界存盘 | **PASS** | 客户端端口 47777：`save` → `{saved:false, netMode:1}`；服务端端口 47778：`save` → `{saved:true, via:"SaveWorld()", netMode:2, path:"...\\蒸汽_险境.wld"}`；文件 mtime 由 07:22:47 → **07:55:52**、大小 2967971 → 2968929 |
| 房屋有效（重做后） | **PASS** | `housediag {x:2125,y:274}` → `{valid:true, tiles:64, box:[2122,2129,272,279], light:1, comfort:2, missing:[]}` |

### 第六轮确认的三条硬规则

1. **存盘必须发给世界宿主**：Host&Play 会开两个进程（无参客户端 + `-server` 持世界）。客户端 `netMode:1`，它存不了盘；服务端 `netMode:2` 才能 `SaveWorld()`。所以桥要按 `Main.dedServ`/`-server` 参数分端口（客户端 47777、服务端 47778），存盘走服务端。
2. **`WorldFile.CreateMetadata` 的第一个参数是"世界名"，不是路径**：把全路径塞进去会被净化成 `C--Users-...-蒸汽_险境_wld.wld`，于是"存盘返回 true、真文件没动"。判定存盘是否成功，必须看**目标 .wld 的 mtime**，不能只看返回值。
3. **`OpenDoor` 不是实心方块**：开着的门会让洪水填充漏出去（`box` 涨到 9001 格、`valid:false`），必须先把开着的门拆掉、再用石/门封上；`ClosedDoor` 才算围合。

### 本轮新增四条硬事实
1. **`craft` 不检查合成站距离**：站在离工作台 24 格的地方照样合成成功（原版工作台配方要求站在工作台旁）。工具层给的是“材料够就能做”，跟游戏规则不一致——涉及“像个人玩”的场合要先走到站旁再合成，别依赖这个便利。
2. **房子里是死胡同**：`ClosedDoor` 关着 + 门外没有落脚空间时长住在里面出不来（`move` 四向无效、`interact` 开门返回 true 但门不动）；**脱困最省事的是 `mirror`**（回到出生点，不破坏房子结构、不影响 `housediag`）。
3. **地形不需要就刷不出“铺路”**：B03 想验证“批量放置”，但这段路本身是实心的，`place` 一次都没调用；要真正验证得挑“必须造桥”的地形（水面、深谷）。
4. **`scan` 的 `tiles` 是“按行的二维数组”**：`tiles[j][i*stride + fieldIndex]`，字段顺序看 `fields`（type|wall|liquid|liqType|shape）；按一维下标读会全是 0——这一条曾让我把整张地形图读成空的。

| 项 | 结果 | 证据 |
|---|---|---|
| K07 铁镐链 | **改题** | 本世界 `find type:6`（铁矿）/`9`（银矿）在 ±70×90 窗口内 **各 0 个**，只有 `166` 锡 62 个、`168` 钨 43 个 → 这世界没有铁，K07 应改成**锡镐**（`id 3503 = 锡锭×8 + 木材×4`） |

### 本轮新增四条硬事实
1. **矿石按世界类型分档**：铁/铅档与锡/钨档互斥，另有一档铜/银/金/铂金；同一张图里只会出现其中一套。写用例时不能写“去挖铁矿”——要先 `find` 确认这套图有哪些矿。
2. **桥命令 `mine` 只负责“挥下去”，不等结果**：直接调它必然出现“命令成功但方块还在”（我用裸桥命令连试 60 次全失败）。正确入口是新工具层的 `primitives.mineTile({x,y})`，它内部反复重挥 + 回读，失败会明确返回 `mined:false`。
3. **`inventory.free` 长期是 0 也不会报错**：挖掘/拾取全部静默失败，唯一征兆是“挖了很多但背包没变”。每轮开工前应先看 `free`。
4. **出生点周边地形已被我挖坏**：1 格宽竖井/悬空平台/塌陷坑连片，`move` 与 `walkto` 都会卡死在同一坐标；进这种区域前应先 `mirror` 回地面，或从外部重新开一条直达通道。

### 重要自我纠错（推翻上一轮写下的结论）
上一轮我写“`craft` 不检查合成站距离”——**错了**。这轮在野外 `craft 703` 直接报 `附近没有这个配方需要的工作站（工作台/熔炉/铁砧…）`。
真相是：**木平台本身就是徒手配方**（不需要工作台），所以我上一轮站在远处也能做；而熔炼、工具类配方都严格查站。KB 已改正。

### 本轮三条硬事实
1. **工具与锭分属不同站**：金属锭在熔炉、金属镐/斧/锤/剑在铁砧、基础物件在工作台；`craft` 报 `附近没有这个配方需要的工作站` 时先分清缺哪个站，再去造那个站。
2. **铁砧是金属工具的硬门槛**：铁砧/铅砧 = 5 锭；没有铁的世界要先攒够 5 铅锭（15 铅矿）。
3. **“有个走不过去的缺口”要用读格定位再补**：卡在 x2120 的真实原因是 (2117..2119,277) 三格是空气、脚下没有落点；补三块石头后立刻能过。比反复 `move`/`jump` 有效得多。

## 第七轮：合成链考核里的四个新坑（2026-10-26）

### 1. `craft` 在背包满时**静默丢产物**
- 现象：背包 `free:0` 时 `craft 704 times:5` 返回 `{"crafted":5,"dropped":0}`，但背包里没有铅锭，8 格半径内也没有掉落物（`grab` → `picked:0, seen:0, actives:12, nearest:"凝胶" @42.6`）。
- 判据：`crafted:N` 只代表“尝试成功”，**完成标记必须是背包里真的多出 N 个**。
- 规则：合成前先 `inventory` 看 `free`；`free === 0` 先用 `trash` 清格，再合成。

### 2. `scan` 的 `tiles` 是“行数组”，不是可按 stride 平铺的一维表
- 一次 `scan {r:4}` 返回 `w=9,h=9`，但 `tiles[y*w+x]` 会越界（元素是数组，长度与 stride 不对应）。
- 规则：**只判一两个格子用 `tile`**；需要大范围才用 `scan`，且按 `tiles[y][x]` 读，并在 `tiles.length` 上做防御。

### 3. 水平掘进决定通过性的是“头部那一格”
- 实测：脚下一列清空后 `move left` 仍位移 0；逐格探到 `(2129,326)` 实心——角色中心 y≈328.4，碰撞盒顶部落在 326 行。
- 规则：横向开路要清 `round(py)-2 .. round(py)+1` **四行**，只清 `r-1..r+1` 会卡死。

### 4. `travel` 报 `stuck` 后 `move` 可能完全无效
- `travel` 内部也受同一碰撞限制；它停下后人被夹在“未清的头部格”旁，四个方向里只有被清通的方向能动（实测 right/up 可动、left/down 不动）。
- 规则：`stuck` 之后先探四邻，再决定方向；不要盲发 `move`。

### 5. 连接数打爆会用 `ENOBUFS` 伪装成“桥挂了”
- 连续脚本每步 4~6 次请求（含多次 `tile`），几十轮后 `connect 127.0.0.1:47777` 报 `errno -4060 ENOBUFS`；随后 `ping` 两个端口都正常。
- 规则：每步请求数要克制（能 `scan` 一次拿一片就别 `tile` 十次）；报错先 `ping` 再判断。

### 自我纠错：`scan` 的 `tiles` 不是一维平铺数组
我上一轮用 `tiles[j*w*stride + i*stride]` 读，得到一片空白，于是怀疑“读数和世界不一致”。
真实结构：`tiles` 是**按行排列的二维数组**（`tiles.length === h`），每行是 `w*stride` 个数字按格内字段交错：
```js
const cell = scan.tiles[row][col * scan.stride]        // type，-1 表示空气
const wall = scan.tiles[row][col * scan.stride + 1]
const liquid = scan.tiles[row][col * scan.stride + 2]
const liqType = scan.tiles[row][col * scan.stride + 3] // 0 水 / 1 岩浆 / 2 蜂蜜 / 3 微光
const shape = scan.tiles[row][col * scan.stride + 4]   // 0 实心 / 1 半砖 / 2..5 斜坡
```
按这个结构重读 (2094..2100, 274..280)：`tile` 说 (2097,277)=dirt、(2097,276)=Trees，`scan` 同一格给 `2` 与 `5` —— **两条读取路径完全一致**。

## 第 31 轮：G07（开箱取物）PASS —— 以及把箱子 API 用错两次

### 结果
自己造箱子 → 存 → 列 → 取，全链路回读：
| 步骤 | 读数 |
|---|---|
| 熔铅锭 | `craft {item:704}` → `{name:"铅锭", crafted:1}` |
| 造箱子 | `craft {item:48}` → `{name:"宝箱", crafted:1, groupsUsed:1}`（配方组同时认铁锭/铅锭：铁锭×1 + 铅锭×1 就够） |
| 放下 | `place {x:2102,y:283,type:21}` → 回读 `Containers`（`placed:false` 但确实放下了，**回读才是判据**） |
| 存入 | `chest {action:"put", invSlot:20}` → `{put:"锡短剑", chestSlot:0}` |
| 列出 | `chest {action:"list"}` → `items:[{slot:0,id:3501,name:"锡短剑",stack:1}]` |
| 取回 | `chest {action:"take", slot:0}` → `{took:"锡短剑", count:1}` → 再 list 得 `items:[]` |

### 两个必须记住的 API 事实（我在这里绕了三圈）
1. **箱子的参数是 `action`，不是 `op`**：`action:"list" / "take" / "put"`；
   存入用 **`invSlot`**（背包格号），取出用 **`slot`**（箱子格号）。
   写成 `op:"deposit"` 时命令不报错、只是被当成 `list` —— 于是我看到“存完还是空的”。
2. **`chest` 不看你传的 x/y**：它用 `NearChest` 找**离人 6 格内最近**的箱子（`float best = 6f*16f`），
   所以 `chest {x,y}` 里的坐标只是提示，真正操作的是最近那个。

3. **背包列表里的下标 ≠ 格子号**：`inventory.items[i].slot` 才是真格子号。
   我用数组下标当 `invSlot` 传进去，结果取走的是另一格的锡短剑（也正好证明“传入的格号被如实执行”）。

### 顺手学到的第三个坑：别站在要放的家具格上
把熔炉放在 (2101,283)（3×2，占 2100..2102 × 282..283），而人正站在 (2100.6,282.7) —— **人就被卡进家具里**，
`move` 四向全部无效、坐标纹丝不动。处置：把那两格家具挖掉，人立刻能动（`2100.6 → 2104.4`）。
**规则：家具一律放在离身体 ≥2 格的位置。**
