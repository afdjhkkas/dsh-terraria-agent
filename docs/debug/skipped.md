### S6 结论（已解决）

根因是**东墙上有一扇开着的门**。逐格探测房屋四条边的 32 个边界格：

```
non-solid perimeter: 3
["east(2130,273)=OpenDoor","east(2130,274)=OpenDoor","east(2130,275)=OpenDoor"]
```

`OpenDoor` 是**非实心**方块，洪水填充从这三个格子漏进外面的世界，于是 `box` 一路涨到 `[2125,2162,1,338]`、`tiles` 涨到 9001。
另外西侧那扇门在之前的下挖里被我挖掉了（三格全 air），等于同时开了第二个口子。

修复顺序（全部真机执行并回读）：

1. 用镐打掉西侧残留的 `ClosedDoor`（`mine` 一次会把 3 格门一起打掉）→ (2121,273..275) 变 air，人可以进屋。
2. 进屋到 (2128.2,278.7)，`mine` 打掉东侧 `OpenDoor`（2130,273..275 三格变 air）。
3. `place {type:1}` 把 (2130,275)(2130,274)(2130,273) 依次砌成 Stone —— 回读三格都是 `Stone`。
4. 回到 (2123.5,278.7)，`place {x:2121,y:275,type:10}` 重新装门 —— 回读 (2121,273..275) 都是 `ClosedDoor`。
5. `housediag {x:2125,y:274}` → **`valid:true, tiles:64, box:[2122,2129,272,279], missing:[]`**。

**教训**：`place` 对着 `OpenDoor` 放方块会返回 `armed:true` 但格子仍是 `OpenDoor`（多格家具不能被单格方块覆盖）；必须先打掉再用真方块砌。

## S7 世界存盘不可用（**已解决**：根因是连到了世界客户端，改成服务端端口 47778 + 直接 SaveWorld）

`save` 命令两条路径全部失败，堆栈完全一致：

```
NullReferenceException
  at Terraria.IO.WorldFile.SaveFileFormatHeader(BinaryWriter writer)  WorldFile.cs:line 925
  at Terraria.IO.WorldFile.SaveWorld_Version2(BinaryWriter writer)    WorldFile.cs:line 902
  at Terraria.IO.WorldFile.InternalSaveWorld(Boolean, Boolean)        WorldFile.cs:line 681
  at Terraria.IO.WorldFile.SaveWorld(Boolean, Boolean)                WorldFile.cs:line 647
  at Terraria.IO.WorldFile.SaveWorld()                                WorldFile.cs:line 623
```

已排除的假设：

1. `Main.ActiveWorldFileData == null` —— 试过无条件 `WorldFile.CreateMetadata(...)` 覆盖重建（`madeMeta:true`），NRE 位置不变。
2. 参数组合 —— `SaveWorld()` 与 `SaveWorld(false,false)` 报同一个行号。

**后果（很重要）**：所有世界改动只在内存里。重启游戏（`deploy2.ps1`）会回滚到上一次成功保存点。本轮出现的“房子修好 → 重启后又坏了”就是这个原因，不是房屋判定复活。

**下一步线索**：

- `api {type:"WorldGen",member:"Save"}` 里有 `WorldGen.saveAndPlay()` / `saveAndPlayCallBack` / `saveToonWhilePlaying()` —— 这是 Host&Play 自己的存盘链路，可能是唯一能走通的路（但要确认它不会把 `Main.gameMenu` 置真把玩家踢回主菜单）。
- 也可以尝试把 `Main.ActiveWorldFileData` 的每个字段（Seed / GameMode / CreationTime / WorldGeneratorVersion / UniqueId）逐项打印出来，看 line 925 到底在读哪个 null 成员。

## S9 专用服务端反复抢占世界 —— 本档最耗时的环境冲突

**现象（出现两次，表现完全一样）**：
- `state.player.grounded` 恒 `true`，但脚下 4 行都是 `hasTile:false` 的空气；
- `mine` 返回 `mode:"player"` + 正确 `held`，但坐标一格不动；
- `travel` 返回 `targetX` 已到、`steps:0`；
- `tile` 对同一格前后两次调用可以给出不同答案（先 `#` 后空）。

**根因**：机器上同时有两个 tModLoader 进程：
```
70848  "…dotnet.exe" tModLoader.dll                      ← 客户端（deploy2.ps1 启的）
26968  "…dotnet.exe" tModLoader.dll -server -autoshutdown ← 专用服务端（不是我启的）
```
世界归服务端，客户端只是连上去的画面进程：**玩家物理不在本地进程里**，本地 tile 读取也不可靠。
单进程 host&play 时一切正常（本轮前半段：`travel 2097→2117`、`jump 273→268→271`、`mine` 真的挖掉格子）。

**判定办法（3 秒）**：`Get-CimInstance Win32_Process | ? { $_.CommandLine -like '*tModLoader.dll*' }`，
多于一个 `-server` 行就是本问题。

**两个可选修法**：
1. 测试期间只跑单进程（`deploy2.ps1` 会自动杀掉所有 tModLoader 进程再起客户端 host&play）；
2. 让桥接同时持有服务端连接（47778），把"动作类"命令发给服务端、把"观察类"命令留给客户端。
   代价：两边的 tile 视图可能不一致，需要额外做一致性校验。
